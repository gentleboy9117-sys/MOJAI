1. 핵심 개념 정리

RSS Really Simple Syndication

언론사·포털이 새 콘텐츠 목록을 표준 형식으로 배포하는 공식 구독 채널.

핵심 특징
  • 공식 배포 채널: 사이트를 긁어가는 것이 아니라, 제공자가 배포용으로 공개한 목록을 받는 구조 — 저작권·약관 부담이 적음
  • 주제별 구독: 키워드·카테고리 단위로 새 글만 받아볼 수 있음
실생활 예시

팟캐스트 앱의 채널 구독, 뉴스 리더 앱(피들리 등)의 언론사 구독이 모두 RSS 기반.

우리 시스템 — 구글뉴스가 제공하는 주제별 RSS('검찰', '중대재해' 등 약 30개 주제)를 구독해 새 기사 목록을 받습니다.
"RSS는 언론이 공식 배포하는 채널이라 무단 수집 논란이 없습니다."

API Application Programming Interface

서로 다른 프로그램이 정해진 규칙에 따라 데이터와 기능을 주고받는 통신 창구.

핵심 특징
  • 소프트웨어 간 통신: 서로 다른 프로그램이 데이터를 공유하고 기능을 함께 사용
  • 복잡한 내부 숨기기: 상대 시스템의 내부 구조를 몰라도 정해진 규칙만 따르면 이용 가능
  • 개발 시간 절약: 검증된 기존 서비스를 가져다 쓰므로 직접 개발 불필요
실생활 예시

날씨 앱(기상청 데이터 요청), 배달 앱 속 카카오 지도, 웹사이트의 네이버·카카오 소셜 로그인.

우리 시스템 — 네이버 뉴스 검색 API로 기사 목록·원문 주소를 받고, 카카오맵 API로 전국 검찰청 지도를 표시합니다.
"네이버·카카오가 공식 제공하는 API를 규칙대로 사용합니다."

크롤링 Crawling / 자동 수집

프로그램이 웹 페이지를 주기적으로 방문해 공개된 정보를 자동으로 수집하는 기술.

핵심 특징
  • 반복 작업의 자동화: 사람이 매일 수십 개 사이트를 도는 일을 프로그램이 대신
  • 적법성은 대상·방식에 좌우: 공개 정보를, 공식 채널로, 서버 부담 없는 주기로 수집하는 것이 원칙
실생활 예시

구글·네이버 검색엔진이 전 세계 웹을 수집·색인하는 것, 가격비교 사이트의 쇼핑몰 가격 수집.

우리 시스템 — 뉴스는 RSS·API(공식 채널)로, 집회 신고 정보는 전국 지방경찰청의 대국민 공개 게시판에서 수집합니다.
"공식 제공 채널과 국민 공개 게시물만, 서버에 부담 없는 주기로 수집합니다."

규칙 기반 분류 Rule-based Classification

사람이 정의한 키워드 사전과 조건 규칙으로 데이터를 분류하는 방식. AI(기계학습)와 대비되는 전통적 기법.

핵심 특징
  • 설명 가능: 어떤 키워드 때문에 그렇게 분류됐는지 근거를 항상 제시할 수 있음
  • 비용 없음·즉시 수정: AI 호출 비용이 없고, 사전만 고치면 즉시 반영
  • 한계: 사전에 없는 표현은 놓침 → 그래서 LLM 보조와 결합(하이브리드)
실생활 예시

이메일 스팸함의 차단 단어 목록, 은행의 이상거래 탐지 1차 룰(금액·시간대 조건).

우리 시스템 — 검찰청 67곳의 관할 지역·경찰서 사전 + 범죄유형 16개의 키워드 사전으로 1차 분류하고, 매칭 근거와 신뢰도를 기사마다 저장합니다.
"1차는 규칙 기반이라 AI 없이도 동작하고, 분류 근거를 항상 제시할 수 있습니다."

LLM Large Language Model · 대형언어모델

방대한 텍스트로 학습되어 언어를 이해·생성하는 AI 모델. ChatGPT·Claude·Gemini가 대표적.

핵심 특징
  • 범용 언어 능력: 요약·분류·초안 작성 등 언어 작업 전반에 활용
  • 확률적 생성: 정답을 '알고' 말하는 게 아니라 가장 그럴듯한 문장을 생성 → 환각 위험의 근원
  • 호출 비용: 사용량(토큰)에 비례해 비용 발생 → 호출 최소화 설계가 중요
우리 시스템 — 규칙 분류의 신뢰도가 낮은 경우에만 LLM이 보조로 개입합니다. 주 분류기가 아니므로 비용과 환각 위험이 모두 낮고, LLM 없이도 시스템은 동작합니다.
"LLM은 규칙 분류가 약할 때만 보조로 씁니다 — 주인공이 아니라 보조입니다."

환각 Hallucination

LLM이 사실이 아닌 내용을 그럴듯하게 생성하는 현상. 확률적 문장 생성이라는 원리에서 비롯되는 구조적 한계.

실생활 예시

미국에서 변호사가 ChatGPT가 지어낸 가짜 판례를 서면에 인용해 제재받은 사건(2023, Mata v. Avianca).

우리 시스템의 3중 통제
  • 입력 범위 제한: 사실관계는 담당자 입력값과 공개 기사 범위 안에서만 작성
  • 양식만 학습: 기존 문서는 형식·문체만 참조, 내용은 사용하지 않음
  • 사람 검토 전제: 모든 산출물에 '참고용 초안' 명시 + 담당자 검토 후 사용
핵심 논거 — 모니터링 화면(수집·집계)에는 생성 과정 자체가 없어 환각이 개입할 여지가 없고, 환각은 '생성' 단계(초안)에만 해당하는 문제인데 그 단계를 3중으로 통제한다는 구조입니다.
"환각은 생성 단계의 문제인데, 저희는 생성 범위를 입력값으로 묶고 최종 검토는 사람이 합니다."

파인튜닝 vs 프롬프트 Fine-tuning / Prompt

파인튜닝은 모델 자체를 추가 데이터로 재학습시키는 것, 프롬프트는 모델에 주는 지시문을 정교하게 설계하는 것.

비교
  • 파인튜닝: 고비용·전문 인프라 필요, 학습 데이터가 모델에 흡수됨(유출 리스크 관리 필요)
  • 프롬프트: 저비용·즉시 수정 가능, 데이터가 모델에 남지 않음
우리 시스템 — 파인튜닝을 하지 않았습니다. 서울중앙지검이 공개 배포한 보도자료 5건의 형식·문체를 분석해 프롬프트 규칙으로 만들었을 뿐, 별도 모델 학습이 없어 학습 데이터 유출 이슈가 원천적으로 없습니다.
"모델 학습 없이 프롬프트 규칙만 사용해, 학습 데이터 유출 이슈가 없습니다."

클러스터링 Clustering · 이슈 묶음

유사한 데이터를 자동으로 묶어 그룹화하는 기법. 본 시스템에서는 동일 사건을 다룬 여러 기사를 하나의 '이슈'로 묶는 데 사용.

실생활 예시

구글뉴스·네이버뉴스의 "관련기사 32건 모아보기", 사진 앱이 같은 인물 사진을 자동으로 묶는 기능.

우리 시스템 — 제목 정규화와 키워드 유사도로 동일 사건 보도를 묶어, '기사 30건'이 아니라 '사건 1건(보도 30건)' 단위로 봅니다. 현재 약 2,600개 이슈로 관리 중.
"동일 사건 중복 보도를 하나의 이슈로 묶어 사건 단위로 파악합니다."

파급도 0~100 정량 지표

이슈의 사회적 주목도를 보도량·출처 수·확산 속도로 산정한 자체 정량 지표.

산정 요소
  • 보도량: 해당 이슈를 다룬 기사 수
  • 출처 수: 서로 다른 언론사 수(한 곳의 반복 보도와 구별)
  • 확산 속도: 최근 24시간 내 보도 증가율
  • 가점 요소: 검찰청 직접 언급 +10 · 사회적 파급 키워드(그룹당 6, 최대 24) · 복수 관할 +8 · 공식자료+언론 동시 +8 — 합산 100점 상한, 80+ 매우 높음
우리 시스템 — 산정 근거가 이슈마다 저장되고 가중치는 관리자가 조정 가능합니다. 담당자의 판단을 대체하는 것이 아니라 수치로 뒷받침하는 보조 지표입니다.
"공개 보도 기반의 정량 지표이고, 산정 근거가 저장되며, 최종 중요도 판단은 담당자가 합니다."

DB · PostgreSQL 데이터베이스

데이터를 구조화해 저장·검색하는 시스템. PostgreSQL은 전 세계 정부·기업이 널리 쓰는 오픈소스 표준 DB.

핵심 특징
  • 오픈소스·무료: 라이선스 비용 없음, 특정 업체 종속 없음
  • 이식성: 클라우드에서 기관 내부 서버로 데이터 이전이 표준 절차로 가능
우리 시스템 — 기사 약 8,700건·이슈·집회·산출물 이력을 PostgreSQL에 저장합니다. 기관 도입 시 내부 서버의 PostgreSQL로 그대로 이전 가능합니다.
"표준 오픈소스 DB라 기관 내부 인프라로 그대로 옮길 수 있습니다."

GitHub · 형상관리 Version Control

소스코드의 모든 변경 이력을 기록·보존하는 저장소 서비스. 세계 개발 표준.

핵심 특징
  • 전체 이력 보존: 언제, 무엇을, 왜 고쳤는지 전부 기록 — 감사·검증 가능
  • 인수인계 용이: 저장소만 넘기면 다른 개발 조직이 즉시 이어받을 수 있음
우리 시스템 — 개발 전 과정이 GitHub에 기록돼 있어, 유지보수 이관·보안 감사 시 그대로 제출할 수 있습니다.
"전체 개발 이력이 보존돼 있어 누구든 인수·검증할 수 있습니다."

자동 배포 CI/CD · Netlify

코드를 저장소에 올리면 빌드·검증·서비스 반영까지 자동으로 진행되는 체계.

실생활 예시

스마트폰 앱이 밤사이 자동 업데이트되는 것과 유사 — 사람이 서버에 들어가 수동 설치하는 과정이 없음.

우리 시스템 — 코드 저장 → 수 분 내 서비스 자동 반영. 배포 과정의 사람 실수가 구조적으로 차단됩니다.
"코드 저장만으로 서비스에 자동 반영되는 표준 배포 체계입니다."

스냅샷 사전 생성 데이터

자주 조회되는 통계·목록을 미리 계산해 파일로 저장해 두고, 조회 시 그 파일을 읽게 하는 성능 기법.

핵심 효과
  • 속도: 매 조회마다 DB 계산을 반복하지 않아 화면이 즉시 뜸
  • 확장성: 동시 사용자가 늘어도 서버 부하가 거의 증가하지 않음
우리 시스템 — 대시보드·순위·지도 등 조회 화면은 스냅샷을 읽는 구조라, 청 단위 확대에도 인프라 증설이 거의 필요 없습니다.
"조회 화면은 사전 생성 데이터를 읽는 구조라 사용자 증가에 강합니다."

클라우드 vs 온프레미스 Cloud / On-premise

클라우드는 외부 사업자의 서버를 빌려 쓰는 방식, 온프레미스는 기관 내부에 서버를 두고 직접 운영하는 방식.

공공 도입 관점
  • 클라우드: 구축 빠르고 저렴하나, 데이터 소재지·보안 규정 검토 필요
  • 온프레미스: 보안 통제 용이 — 공공 내부 시스템의 기본값
우리 시스템 — 현재는 시연용 클라우드이며 올라간 데이터는 전부 이미 공개된 언론보도 메타데이터입니다. 특정 클라우드 전용 기능을 쓰지 않아, 도입 시 내부 서버(온프레미스)로 이전이 쉽습니다.
"현재 클라우드엔 공개 기사 데이터만 있고, 도입 시 내부 인프라 이전을 전제로 설계했습니다."

망분리 · 단방향 폐쇄망 대응 구조

망분리는 업무망(내부망)을 인터넷과 물리·논리적으로 분리해 운영하는 공공 보안 체계. 단방향은 정보가 외부→내부 한 방향으로만 흐르는 구조.

우리 시스템의 구조
  • 수집은 외부망: 공개 정보 수집은 인터넷 구간에서 수행
  • 처리는 내부망: 수집된 자료만 내부로 반입해 분석·표시
  • 유출 차단: 내부 정보를 외부로 내보내는 경로 자체가 없음
답변 방어선 — 방향(단방향)은 확정적으로 말하되, 반입 방식 등 세부는 "기관 IT·보안 부서와 협의해 단계적으로"로 고정. 세부까지 단정하면 오히려 공격받습니다.
"외부 정보를 수집하되 내부 정보를 유출하지 않는 단방향 구조이며, 세부 구성은 기관 보안 규정에 따릅니다."

KICS 형사사법정보시스템

경찰·검찰·법원·법무부가 사건 기록과 형사사법정보를 처리하는 공동 내부 시스템.

우리 시스템과의 관계 — 완전 분리. 형사사법정보·수사정보는 일절 다루지 않고, 인터넷 공개자료(언론보도·공개 게시판)만 사용합니다. 연동은 기술적으로 가능한 '옵션'이며, 여부·범위는 운영기관이 결정할 사안입니다.
"KICS와 완전히 분리돼 있고 형사사법정보는 일절 다루지 않습니다. 연동은 향후 기관이 결정할 옵션입니다."

KRDS 범정부 디자인 시스템

행정안전부가 정한 정부 디지털 서비스의 표준 화면 설계 가이드. 정부24 등 공공 웹사이트의 공통 디자인 기준.

우리 시스템 — KRDS 기준으로 화면을 구성해, 공공 서비스 정식 전환 시 UI 재작업 비용이 최소화됩니다.
"KRDS 표준을 적용해 공공 전환 시 화면 재작업이 최소화됩니다."

SSO · 권한 관리 Single Sign-On

SSO는 기관 계정 하나로 여러 시스템에 로그인하는 통합 인증. 권한 관리는 사용자별로 열람·수정 범위를 구분하는 것.

실생활 예시

회사 포털에 한 번 로그인하면 메일·결재·인사 시스템이 함께 열리는 것.

우리 시스템 — 현재는 시연용 단일 계정이며, 도입 시 기관 인증체계 연동과 열람/관리 권한 분리를 전제로 설계돼 있습니다.
"도입 시 기관 SSO에 연동하고 권한을 분리하는 것을 전제로 합니다."

정적 분석 · 보안성 검토 Static Analysis

프로그램을 실행하지 않고 소스코드 자체를 도구로 검사해 보안 취약점·결함을 찾는 기법. 공공 정보화 사업의 표준 검증 절차.

우리 시스템 — AI가 작성한 코드도 타입 검사·빌드 검증을 상시 통과시키고 사람이 리뷰했으며, 정식 도입 단계에서 정보보안 부서의 정적 분석·보안성 검토를 받는 것을 전제로 합니다.
"AI 생성 코드도 사람이 리뷰했고, 도입 시 표준 보안성 검토를 전제로 합니다."

바이브 코딩 Vibe Coding · AI 페어 개발

개발자가 아닌 사람이 요구사항을 자연어로 설명하면 AI가 코드를 작성하고, 사람은 결과를 검증하는 개발 방식.

핵심 포인트 (Q&A 최다 출제 예상)
  • 개발 도구 ≠ 운영 부품: Claude Code는 개발 단계의 도구였을 뿐, 완성된 시스템의 운영에는 필요 없음
  • 실무자 직접 개발의 의미: 현장 요구사항 정의(무엇을)와 검증은 실무자가, 구현(어떻게)은 AI가 — 외주 개발의 소통 손실이 없음
  • 품질 통제: 표준 스택 + 상시 검증 + 사람 리뷰로 보완
"Claude Code는 개발 단계의 도구였고, 운영에는 필요 없습니다. 지금도 Claude Code 없이 자동으로 돌고 있습니다."

2. ★최우선 16문항 — 셀프 테스트

질문을 읽고 소리 내어 답한 뒤, 클릭해서 요지·논리를 확인하세요.

지금 실제로 작동하는 시스템인가?

실제 운영 중이며 지금 이 자리에서 접속 가능. 기사 약 8,700건·이슈 약 2,600건, 오늘 아침 수집분까지 반영.

완성도 30점의 관문 질문 — 형용사 대신 검증 가능한 숫자와 '즉석 접속 제안'으로 답한다.

Claude Code가 있어야 수집·운영되는 것 아닌가? 공직 도입이 어려운데 대안은?

아니다. Claude Code는 개발 단계의 도구였고 운영에는 불필요 — 수집·분류·초안 생성은 완성된 코드가 자체 실행되며 지금도 Claude Code 없이 돌고 있다. 운영 중 AI(분류 보조·초안)는 별개 사안으로 ①규칙만 ②상용 API ③내부망 AI 중 선택 가능. 유지보수도 표준 스택이라 일반 개발 인력으로 가능하고, 기관 승인 개발용 AI가 있으면 더 빠를 뿐이다.

'개발 도구'와 '운영 부품'의 혼동을 바로잡는 것이 답의 전부. 이 구분만 명확하면 한 번에 정리된다.

"기능 추가 때는?" → "표준 코드라 일반 개발자가 수행 가능합니다. AI 도구는 속도의 문제이지 가능 여부의 문제가 아닙니다."

분류는 어떤 방식인가? LLM인가?

하이브리드 — 1차는 규칙 기반(관할 67곳·유형 16개 키워드 사전, 신뢰도 스코어링), 신뢰도가 낮을 때만 LLM 보조. AI 없이도 동작한다.

"전부 LLM"이라 답하면 환각·비용·재현성 공격이 이어진다. '규칙이 주, LLM이 보조'가 방어의 축.

"규칙은 누가 만들었나?" → "검찰 실무 지식으로 제가 설계했고, 관리자가 사전만 수정하면 즉시 반영됩니다."

분류 정확도는? 오분류가 나면?

시범 단계라 다소 부정확한 분류가 있을 수 있음을 먼저 인정. 다만 ① 분류 근거·신뢰도가 기사마다 저장돼 검증·수정 가능 ② 오분류는 동일 패턴 소급 정정 + 기준 보완까지 일괄 수행 ③ 정식 출범 후 데이터 축적·사전 고도화·AI 보조 학습으로 정확도가 지속 상승하는 구조.

한계를 숨기지 않되 '개선되는 구조'로 마무리 — 겸손+성장 프레임이 신뢰를 만든다.

"정확도 수치를 제시하라" → "벤치마크 수치는 시범 운영에서 검증 데이터셋으로 산출하겠습니다."

환각은 어떻게 통제하나?

① 사실관계는 입력값·공개자료 범위 안에서만 ② 문서는 양식·문체만 참조 ③ '참고용 초안' 명시+담당자 검토. 그리고 모니터링 화면은 생성이 아닌 수집·집계라 환각이 개입할 단계 자체가 없다.

'집계'와 '생성'을 구분해 답하면 AI 전문위원에게 구조를 이해하고 있다는 신호가 된다.

폐쇄망에서 실제로 되나? 지금은 인터넷이지 않나.

오늘은 인터넷망 시연이며, 도입 시 3구간 구성 — ① 외부망 수집 서버(수집+1차 필터링) ② 기관이 이미 운영 중인 표준 망연계 시스템으로 텍스트 데이터를 주기 배치 단방향 반입(신규 장비 불요) ③ 내부망 서버(분류·집계·화면·초안). 내부→외부 전송 경로는 없음. 전송 주기·포맷·검역 등 세부는 보안 부서와 협의.

방향은 단정, 세부는 협의 — 세부까지 단정하면 보안 전문가의 반격 지점이 된다.

KICS와 연동하나? 형사사법정보는?

완전 분리. 형사사법정보·수사정보는 일절 다루지 않고 인터넷 공개자료만 사용. 연동은 향후 운영기관이 결정할 옵션.

개인정보 침해 소지는?

수집 대상이 언론이 이미 공개 보도한 기사와 공공기관 공개 게시물뿐 — 별도 개인정보 수집이 없다. 산출물은 실명 단정 표현을 피하고('A씨' 원칙) 무죄추정 표현을 쓰며, 공개 판단은 공보 담당자가 한다.

언론사 저작권 문제는?

원문 전문을 무단 저장·표시하지 않는다 — 제목·출처·링크 중심으로 표시하고 클릭 시 원문 이동. 기사별 라이선스 구분을 관리하며, 정식 도입 시 뉴스 이용 계약으로 정식화한다.

'1시간 → 5분'의 근거는?

본인 담당 시절 실측 경험 기준(포털 검색 수십 회+수기 분류+정리 = 1시간 이상 → 대시보드·Top10·브리핑 3단계 = 5분 내외). 복수 담당자 실측은 시범 운영에서 확보 예정.

과장하지 않는 정직한 구조(경험치+검증 계획)가 신뢰를 만든다.

다른 검사·직원이 사용해 봤나?

현재는 본인 실사용 단계. 본선 이후 소속청 담당자 시범 사용을 계획 중이며, 설치가 필요 없는 웹 방식이라 시범 확대 비용이 들지 않는다.

개발자가 1명인데 유지보수는 누가 하나?

표준 스택(TypeScript·Next.js·PostgreSQL)과 GitHub 전체 이력 덕분에 어느 개발 조직이든 인수 가능. 정식 도입 시 법무부 정보화 조직/유지보수 사업자로 이관하고, 본인은 도메인 지식 전수로 지원.

'나 없으면 안 된다'는 인상이 최악 — '표준이라 누구나 이어받는다'로 프레임.

기존 서비스(빅카인즈 등)와의 차별점은?

기존 서비스에 없는 3가지 — ① 검찰청 67곳 '관할' 개념 ② 범죄유형·공판·공안이라는 검찰 업무 분류 ③ 검찰 양식 산출물(브리핑·보도자료·문자풀). 범용 뉴스 검색을 검찰 업무 구조로 재구성했다.

타 기관 확산에 실제로 무엇을 바꿔야 하나?

기본 기능(수집·분류·집계·초안 작성)은 지금 제품 그대로 적용. 새로 만들 것은 사실상 분류 기준 하나 — 기관 관심 주제 키워드를 실무자 논의로 정의해 학습시키면 되고, 조직도·문서 양식은 기존 자료를 그대로 학습. "맡겨 주시면 첫 확산 기관까지 제가 직접 해내겠습니다."

"수 주의 근거는?" → "코드 수정이 아니라 사전·조직표 데이터 교체 수준이기 때문입니다. 실제로 관할 기준 보완을 하루 안에 반영한 경험이 있습니다."

법무부 도입 시 어떤 순서를 제안하나?

3단계 — ① 검찰 1~2개 청 시범(즉시 가능) ② 법무부 실·국 확산(설정 교체) ③ 망분리 정식 도입(내부 이전+보안성 검토). 각 단계의 결과가 다음 단계의 검증 자료가 된다.

시스템이 놓치거나 잘못 판단하면 책임은?

시스템은 판단하지 않는다 — 수집·분류·초안까지만 수행하고, 채택과 최종 문안은 담당자가 결정. 화면에 '공개 보도 기준 참고용' 명시. 도구가 책임 구조를 바꾸지 않는다.

4. 답변 공식

① 결론부터 한 문장 — "예/아니오/~입니다"로 시작. 배경 설명으로 시작하면 5분이 소진된다.

③ 한계 인정 + 보완 방향 — "다만 ~는 시범 운영에서 검증하겠습니다."
모르는 세부 질문 — "정확한 수치는 서면으로 보완드리겠습니다. 설계 방향은 ~입니다." (외부 AI 위원 앞에서 아는 척은 즉시 간파된다)
불리한 질문은 개선 구조로 회귀 — "시범 단계의 한계는 인정하되, 쓸수록 정확해지는 구조입니다" · "판단은 사람의 몫입니다" · "공개자료만, 단방향, 세부는 기관 협의"
