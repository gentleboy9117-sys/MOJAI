## ① 검토 배경 (업무 배경 및 문제 상황)

**■ AI 도입 계기**

기획·공보 업무를 담당하는 검사는 매일 아침 **언론보도·공개자료를 광범위하게 모니터링**해야 합니다.
- 주요 형사사건의 **수사·기소·선고(공판) 동향**
- **집회·시위 등 공안 동향**
- **검찰개혁·보완수사권·공소청 등 형사사법 제도/정책 이슈**
- 그리고 사건 처리 후 **보도자료(발표자료) 작성**

이 정보들은 매일 수백~수천 건씩 쏟아지지만, **"어느 검찰청 관할 사건인지", "어떤 범죄유형인지", "오늘 선고가 난 사건인지"** 를 사람이 일일이 읽고 분류해야 합니다. 단순 반복이면서도 누락 시 보고 품질에 직결되어, **고급 인력이 가장 가치 낮은 작업에 시간을 빼앗기는** 전형적 구조였습니다.

**■ AI 활용 이전의 업무 현황과 불편했던 점**

| 작업 | 기존 방식 | 불편 |
|---|---|---|
| 기사 수집 | 포털·언론사 수동 검색 | 매일 30분~수시간, 누락·편향 |
| 관할 분류 | 제목만 보고 수기 추정 | 발행 지역≠사건 관할이라 오분류 빈발 (예: 부산일보 보도라도 사건은 서울중앙지검) |
| 중복 정리 | 같은 사건 여러 기사 수기 취합 | 동일 사건이 수십 건으로 부풀려져 체감 왜곡 |
| 공판 추출 | 선고 기사 일일이 확인 | 미래 선고·민사·가사 사건과 혼동 |
| 보도자료 초안 | 백지에서 직접 작성 | 형식·문체 표준화 부담, 표현 리스크 검토 누락 |

## ② 활용한 AI 도구·서비스 (활용 방법 및 구현)

**■ 사용한 AI 도구·서비스**
- **Anthropic Claude API** — 분류·요약·초안 생성 등 자연어 처리의 핵심 엔진
- **바이브 코딩(Vibe Coding)** 으로 직접 개발한 **풀스택 웹 애플리케이션**
  - 프런트엔드: Next.js(App Router)·TypeScript·TailwindCSS
    - **정부디자인시스템(KRDS, Korea Design System) 기반 UI** — 색상·타이포·간격·구분선·아이콘 등 화면 전반을 **KRDS 디자인 토큰 체계로 통일**해, 별도 학습 없이도 공무원에게 익숙하고 일관된 사용성을 제공합니다. 공식 전자정부 누리집과 동일한 톤이라 **신뢰감·접근성·공공 UI 표준 부합**이라는 측면에서, 실제 정부 서비스로의 즉시 적용·확산에 유리합니다.
  - 백엔드/데이터: PostgreSQL(서울 리전)·Prisma ORM
  - 수집: 네이버 뉴스 검색 API + **기사 본문 크롤링**(서버렌더링 모바일 미러 활용)
  - 분류: **규칙기반 분류 + LLM 보강**의 하이브리드 구조
- 배포: Netlify(상시 접속 가능한 데모 URL 운영)

**■ AI를 어떻게 활용하였는가 (파이프라인)**

```
[1] 수집  : 매일 정기적으로 법조·치안 공개기사 자동 수집
   ↓
[2] 본문 분석·관할 분류 : 기사 "본문" 속 법원·검찰청·경찰서·발생지를 읽어
        관할 검찰청을 판정 (발행사 지역이 아닌 '사건 관할' 기준)
   ↓
[3] 범죄유형 분류 : 강력/경제/부패·공직/마약/디지털/성범죄/선거/조세 등으로 자동 분류
   ↓
[4] 공판·제도이슈 식별 : '오늘·어제 법원 선고' 기사만 공판으로,
        검찰개혁·공소청·특검 등은 제도/정책 이슈로 분리
   ↓
[5] 중복 묶음(dedup) : 동일 사건 다수 보도를 1건으로 통합 + 출처 링크 보존
   ↓
[6] 이슈화·파급도 스코어링 : 유사 기사를 사건 단위로 군집(cluster),
        보도량 기반 '파급도' 점수 산정
   ↓
[7] 산출 : 검찰청별·범죄유형별 현황, 공판 모니터링, 집회·시위 관할별 정리,
        제도/정책 이슈, 그리고 보도자료 초안·문장 리스크 점검까지
```

> 핵심 차별점: 단순 키워드 매칭이 아니라 **기사 본문을 읽어 '사건의 관할'을 판정**한다는 점입니다. 실제로 본문 기반 분석으로 **약 3,000여 건의 관할을 자동 교정**했습니다.

## ③ 활용 결과 및 업무 변화 (도입 전·후 비교)

**■ 구현한 주요 기능**
1. **이슈 모니터링** — 검찰청별 / 범죄유형별 / 제도·정책 이슈 / 자동 브리핑
2. **공판 모니터링** — 당일·전일 법원 선고 사건만 추출, 검찰청별·범죄유형별 정리
3. **집회·시위(공안) 모니터링** — 전국 지방경찰청 공지에서 집회 일정 수집 → 검찰청 관할별 정리
4. **사건 처리 후 발표자료** — 보도자료 초안 자동 생성 · 검찰발표자료 레퍼런스 · **문장 리스크 점검**

**■ 도입 전·후 비교**

| 항목 | AI 도입 전 | AI 도입 후 |
|---|---|---|
| 기사 수집·분류 | 수동 검색·수기 분류 (매일 수십 분~시간) | **자동 수집·분류** (담당자는 결과만 확인) |
| 관할 정확도 | 제목 기반 추정, 오분류 빈번 | **본문 기반 판정**, 약 3,000건 자동 교정 |
| 중복 사건 | 동일 사건 수십 건으로 난립 | **1건으로 통합** + 출처 다수 링크 |
| 무관·노이즈 기사 | 수작업 선별 | 정치·스포츠·연예·해외·홍보성 기사 **자동 필터** |
| 보도자료 초안 | 백지 작성 | **초안 자동 생성 + 표현 리스크 점검** |

**■ 업무 방식의 변화**
- 반복적인 **수집·분류·중복정리·초안작성 시간을 대폭 단축**하고, 담당 검사는 **'무엇이 중요한 이슈인지', '어떻게 대응할지'라는 본질적 판단**에 집중할 수 있게 되었습니다.
- 검찰청 관할 단위로 정리되므로, **전국 동향을 조직 체계(고검–지검–지청) 순서로 한눈에** 파악할 수 있습니다.

## ④ 확산 가능성 및 향후 발전 방향

**■ 타 부서·기관 적용 가능성**
- **전국 모든 검찰청**에 그대로 적용 가능 (관할·조직 체계가 이미 반영됨).
- 모니터링 엔진은 도메인 교체만으로 **법무부 타 부서**(교정·출입국·범죄예방·인권)와 **타 기관**의 언론·정책 모니터링에 재사용 가능.
- **보도자료 초안 생성·문장 리스크 점검**은 정부 부처 공통 업무여서 범용 확산성이 높음.

**■ 한계와, 해결 시 가능한 비약적 개선** (가장 중요한 어필 포인트)

1. **자동 수집의 잠재력** — 현재는 심사 공정성을 위해 **2026.6.26.자로 데이터를 고정**하고 자동 수집을 중단해 두었습니다. 상용화하면 **매일 자동 업데이트되어**, 매일 쏟아지는 정보를 사람이 따라잡을 수 없는 속도로 **체계적으로 분류·요약하는 역동적 도구**가 됩니다. *(즉, 현재 데모는 살아있는 시스템의 '정지 화면'입니다.)*

2. **기사 본문 수집의 한계 → 라이선스·수집권 확보 시 도약** — 현재는 비용 없이 공개 미러로 본문을 우회 수집하다 보니, 자바스크립트 렌더링 언론사 등 **일부 기사는 본문을 못 읽어 '관할 미상'으로 남습니다.** **라이선스 뉴스 API 또는 공식 본문 수집 권한**이 확보되면 **관할 분류 커버리지·정확도·실시간성이 비약적으로 향상**됩니다.

3. **경찰청과의 정보 연계 → 전국 집회 동향 실시간 완전 수집** — 집회·시위 일정은 현재 **전국 18개 지방경찰청 게시판 중 14곳**에서 자동 수집되며, 게시판이 JS/프레임 구조인 4곳은 미수집 상태입니다. **경찰-검찰 간 공식 데이터 연계(API)** 가 이루어지면 **전국 집회 일정을 실시간·빠짐없이** 확보해 공안 대응의 선제성이 크게 높아집니다.

4. **내부망·공식 DB 연계** — 현재는 100% 공개정보만 사용합니다(범죄정보·개인정보 미사용). 향후 보안이 확보된 내부 환경에서 형사사법정보시스템(KICS) 등 **공식 데이터와 안전하게 연계**하면, 공개정보 분석을 넘어 실제 업무 데이터까지 지원하는 도구로 확장될 수 있습니다.
